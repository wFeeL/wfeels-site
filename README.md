# wfeels — сайт-портфолио v3

Astro 7 (статика) + маленький FastAPI для формы заявки и демо-чата.
Спека: `FREELANCE_LAUNCH/70-workshop/specs/site-v3/`.

## Запуск

    cd web && npm install && npm run dev      # http://localhost:4321
    cd api && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
    cd api && .venv/bin/uvicorn app.main:app --port 8000

## Проверки

    cd web && npm run build && npm run test:unit && npm run test:e2e
    cd web && npm run check:budget
    cd api && .venv/bin/pytest

`check:budget` (`scripts/check-budget.mjs`) читает уже собранный `web/dist` и меряет
вес трёх текстовых страниц: `/`, `/contact`, `/privacy`. Пределы — 400 КБ на первую
загрузку страницы и 30 КБ сжатого JS. При превышении команда завершается ненулевым
кодом.

Считается то, что браузер реально скачает: HTML, подключённые из разметки CSS и JS,
плюс шрифты, на которые ссылается CSS, — на них нет ссылок в HTML, и обход только по
разметке потерял бы около 148 КБ, больше трети бюджета. Из подмножеств шрифта
считаются кириллица и латиница; `greek`, `cyrillic-ext`, `latin-ext` и `vietnamese`
разделены по `unicode-range` и не грузятся, пока их символы не встретятся в тексте, —
их учёт завысил бы вес. Видео не учитывается: на текстовых страницах его нет.

Превышение бюджета — находка, а не повод поднять предел: на сайте есть утверждение о
весе страницы, и при перевесе снимать надо утверждение, а не проверку.

## Деплой

Разворачивается двумя контейнерами: `api` (образ из `api/Dockerfile`, uvicorn на
внутреннем 8000, запуск не от root) и внутренний `caddy` (`caddy:2-alpine` на
`127.0.0.1:8088`). Публичный reverse proxy хоста принимает 80/443, выпускает
сертификат и передаёт запросы внутреннему Caddy с исходным `Host`.
API сначала записывает заявку и доказательство согласия в SQLite на постоянном
томе `leads_data`, а уже после успешной транзакции отправляет полную копию в
закрытый Telegram-чат. Сбой Telegram не теряет заявку: доставка остаётся в
очереди базы и повторяется фоновым обслуживанием.

Caddy отдаёт собранную статику `web/dist` сам и проксирует **только** `/api`.
Упавший API не роняет сайт: перестаёт работать форма, а она деградирует в прямую
ссылку на Telegram. Предел размера тела запроса (64 КБ) стоит на Caddy, до
приложения: приложение читает тело в память целиком до валидации.

Страница 404 отдаётся через `handle_errors`, а не последним кандидатом в
`try_files`, — иначе несуществующий адрес вернулся бы с кодом 200 и поисковик
проиндексировал бы его как дубль. `root` объявлен на уровне сайта: обработчику
ошибок тоже нужно, чем отдавать страницу. Отказ на `/api/*` («форма не
отправилась») идёт своей веткой обработчика — с сохранением кода (502, 413) и с
телом, в котором есть дорога назад к форме.

Служебной витрины `/dev/ui` в боевой сборке нет вовсе: файл лежит вне
`web/src/pages/`, а маршрут подставляет интеграция `dev-pages` в
`astro.config.mjs` — только в `astro dev` и при `DEV_PAGES=1` (флаг ставит
`playwright.config.ts`, витрина нужна прогону e2e). Правило `/dev/*` на Caddy
остаётся вторым рубежом: закрывать теперь нечего, но и снимать его незачем.

Контейнер API изолирован: код принадлежит root и процессу приложения только на
чтение, файловая система смонтирована `read_only`; запись разрешена только в
`tmpfs /tmp` и постоянные тома `/data` и `/backups`. Capability сброшены,
повышение привилегий запрещено. Логи обоих контейнеров ротируются (`json-file`,
10 МБ × 3) и не содержат полного текста заявки даже при сбое Telegram.

Бот удаляет Telegram-копию через 23 часа, а таймер закрытого чата auto-delete
«1 день» служит независимым предохранителем. Это укладывается в 48-часовой
предел обычного метода `deleteMessage` Bot API. Основная заявка
хранится 90 дней, доказательство согласия — 1095 дней. Раз в 24 часа SQLite
копируется согласованным API `sqlite3.Connection.backup` в отдельный том
`leads_backups`; локальные копии старше семи дней удаляются. Оба тома находятся
на том же российском VPS: это мера восстановления от повреждения прикладной
базы, но не защита от полной потери VPS. Внешнее резервное хранение нельзя
заявлять до подтверждения его размещения в России.

    cd deploy && cp .env.example .env      # заполнить SITE_DOMAIN, SITE_URL, токен и chat_id бота
    cd ../web && SITE_URL=https://<домен> npm run build
    cd ../deploy && docker compose config  # синтаксис
    docker compose up -d
    docker compose down

Статика собирается перед подъёмом: `web/dist` монтируется в Caddy только на
чтение, сборка внутрь контейнера не входит. Пересобрали сайт — контейнер
перезапускать не нужно.

Проверка внутреннего контура на самом VPS:

    curl -sS -H 'Host: <домен>' http://127.0.0.1:8088/api/health   # {"status":"ok"}
    curl -sSI -H 'Host: <домен>' http://127.0.0.1:8088/            # 200
    curl -sSI -H 'Host: <домен>' http://127.0.0.1:8088/net-takoy   # 404, не 200

После настройки публичного reverse proxy отдельно проверяются
`https://<домен>/api/health`, редирект с HTTP, сертификат и 404 с внешней сети.

Секреты только в `deploy/.env` — он в `.gitignore`. Публичный reverse proxy
хоста и его сертификаты управляются вне этого Compose-проекта. В git лежит
`deploy/.env.example` с пустыми значениями.

Если VPS не имеет прямого доступа к Telegram Bot API, в `deploy/.env` можно
задать прокси только для отправки заявок:

    TELEGRAM_PROXY_URL=http://user:password@proxy.example:8080

Пустое значение означает прямое соединение. Прокси не отключает проверку TLS до
`api.telegram.org` и не применяется к остальному трафику контейнера.
